# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Congress is a personal, self-hosted productivity system for a single user, deployed at `congress.marinprusac.com`. It's a monorepo of **genuinely independent services** — not a single app with logical modules. The full design intent is in `docs/congress-project-brief.md`; read it for the "why" behind anything that looks unusual. Note that two things have changed since that brief was written: the brief specifies Tailscale-only private access, but the deployed system now uses public access gated by a master-password session cookie instead (see `infra/README.md`, "Access control"); and the brief describes one widget per Chamber rendered in an iframe, but Congress's homepage is now a ranked "For You" feed with an AI chat composer, and there are no widgets and no per-Chamber navigation at all — see "Home: feed, views and the shell" below and `docs/creating-a-chamber.md` §5.1 for the current model. Trust `infra/README.md` and this file over the brief on deployment/access and homepage details respectively.

Three names are used consistently in code, folders, and package names:

- **Congress** — both the whole system, and (confusingly, but deliberately — see below) the one backbone service everything else depends on: `services/congress` is the chamber registry, request gateway, session auth, Exhibit cache/search/resolve fan-out, a generic cross-Chamber event relay, the PWA shell (login gate, `ChamberHost`), **and** three core product features: the **home screen** (the feed, pinned views, Search, "+" — formerly the "Capitol" widget canvas), the **event log/notification center** (formerly the "Logs Chamber" — see "Events and Notifications" below), and the system's one **AI** — threaded chat, the asks it sends the owner on its own, its memory, and the proactive engine that decides when it acts (formerly part of the retired Deputy Chamber — see "AI" below). It has no productivity features of its own. It's the one service every Chamber registers with and the only thing Caddy ever points at.
- **Capitol** and **Logs** no longer exist as Chambers — they were folded into Congress as core features (the home screen at `/`, the Notifications tab, event settings/history under Settings → Logs). The name "Capitol" survives only in a few legacy identifiers (`CapitolMark`, `useCapitolSettings`, `capitolSettingsSchema`). `services/congress/src/legacyImport.ts` is a one-time importer of the old Logs SQLite file (and `ai/legacyImport.ts` of Deputy's old AI settings row); both can be deleted once they have run in production.
- **Chamber** — any individual module (`services/chamber-notes`, `services/chamber-calendar`, `services/chamber-documents`, `services/chamber-tasks`, `services/chamber-map`, `services/chamber-fitness`). Each is a fully separate process: own port, own SQLite file, own frontend build, own MCP server. No Chamber imports another Chamber's source, shares a database, or shares a process.

Status vocabulary stays plain in UI/code: a Chamber is `active` or `offline`, never "convened"/"adjourned" — the Congress/Chamber theme is structural, not narrated.

## Commands

There's no root-level dev/build orchestration (no turbo/nx) — work one service at a time with `pnpm --filter <service>`, e.g. `chamber-notes`, `chamber-calendar`, `chamber-documents`, `chamber-tasks`, `congress`.

```bash
pnpm install                                   # once, from repo root

pnpm --filter <service> dev:server             # backend, watch mode (tsx watch)
pnpm --filter <service> dev:web                # frontend, Vite dev server
pnpm --filter <service> build:web              # frontend production build -> frontend/dist
pnpm --filter <service> build:remote           # every Chamber: remote-entry.js/.css for shell-hosting, run after build:web
pnpm --filter congress build:vendor            # Congress only: shared React/router/query-client build the above resolves against
pnpm --filter <service> typecheck              # tsc --noEmit, server + frontend tsconfig

pnpm -r typecheck                              # typecheck every package/service — run this after any change
pnpm typecheck                                 # the above, plus the root tests/ directory

pnpm test                                      # vitest, whole monorepo — run this after any change
pnpm test services/chamber-map                 # any path fragment filters
pnpm test:watch                                # vitest in watch mode

pnpm --filter <service> db:generate            # after editing src/db/schema.ts -> drizzle-kit generate
pnpm --filter <service> db:migrate             # apply migrations locally (also auto-applied on service boot)
```

There is no lint config in this repo — `pnpm typecheck` and `pnpm test` are the two automated checks, and both are expected to pass cleanly before committing.

**A new feature ships with tests for it, in the same change** — not as a follow-up, and not only when asked. This matters more here than in most repos because pushing to `main` is the deploy (see Deployment below): there is no stage between a regression and production. Aim them at stateful and cross-service logic — state machines, caches, matching rules, auth wiring — rather than plain CRUD route handlers, which `strict` + `noUncheckedIndexedAccess` already protect well; the point is to cover what typecheck cannot reach, not to hit every line.

Tests are Vitest, configured once at the root (`vitest.config.mts`) rather than per service, and live beside the code they cover as `src/**/*.test.ts` (plus `tests/` at the root for cross-service checks like the migration smoke test). They run in a Node environment only — there is no jsdom setup, so frontend coverage is limited to `congress-ui`'s pure string helpers, not component rendering. Shared helpers live in `packages/test-support` (`@congress/test-support`) — a workspace package rather than a plain folder, so each service's own `typecheck` (which pins `rootDir` to its own `src/`) can still see them. A few things make this work and are worth knowing before adding a suite:

- Every service opens its SQLite handle and parses its env **at module load** (`src/db/client.ts`, `src/env.ts`). `packages/test-support/src/env.ts` is a Vitest `setupFile`, so it runs before any of that and points `DB_PATH` at a fresh temp file — one per test file, since Vitest gives each test file its own module registry. A test that needs several databases in one file resets with `vi.resetModules()` after moving `process.env.DB_PATH`.
- `runMigrations()`'s default migrations path is relative to the process cwd (the repo root under Vitest), so tests pass an absolute one via `migrationsDir(<service>)`.
- Congress's gateway is tested against a **real** ephemeral upstream (`startFakeChamber`), not a stubbed `fetch` — its behaviour is mostly header and stream handling, which a stub cannot exercise.
- When the logic worth testing is module-private, adding an `export` to it is fine, and pulling a cluster of it into a leaf module next to its caller (the way `geo.ts` and `annotationMatching.ts` sit beside chamber-map's `tracking.ts`/`reprocess.ts`) is better still — both are established here, not a workaround.

`infra/deploy/pre-push-hook-checks` enforces both checks before a push, blocking it on failure for fast local feedback. Install it with `cp infra/deploy/pre-push-hook-checks .git/hooks/pre-push && chmod +x .git/hooks/pre-push`. The same two checks also gate the actual deploy in CI (see Deployment below) — a push that skips the local hook (`--no-verify`) still can't reach production without passing them.

A Chamber's frontend dev server proxies `/api`, `/manifest`, `/health`, `/mcp` to its own backend port, and exhibit search/resolve calls (`/congress/*`) to Congress's dev port (`3000`) — see the `PROXY_TARGET`/`CONGRESS_PROXY_TARGET` constants at the top of each `frontend/vite.config.ts`. In production everything is same-origin through Congress's proxy instead (see Gateway below), which is also why each frontend build sets `base: "/<chamber-name>/"`.

## Architecture

### Repo shape

- `packages/shared-types` — zod schemas and DTOs shared across every service (manifest shape, exhibit search/resolve contracts, settings types). Types and schemas only, never logic — kept small enough that a Chamber written in another language could reimplement its shape from the JSON Schema alone.
- `packages/chamber-kit` — **backend** boilerplate every service composes rather than inherits: `createDb`/`loadEnv`/`createCapitolRegistration`/`createMcpApp`/`createTableBackedExhibits`/`createPushExhibitSync`/`createSingleRowSettings`/the `mount*Routes` Hono helpers. When adding a new Chamber or a new cross-cutting backend concern, check here first for an existing factory before hand-rolling the pattern again.
- `packages/congress-ui` — **frontend** components/hooks shared across every React app: `ChamberLayout`, the Exhibit chip/picker/annotated-text system, dark mode (`useAppliedTheme`), `ViewCard` (a view card's body), `useAiRunStream`, `useBackNavigation`/`ChamberIndexRedirect`, the canonical `ChamberMarks` icon set. Source-only workspace package, consumed via `@congress/congress-ui` (components) and `@congress/congress-ui/styles.css`.
- `services/<name>/src` — backend (Hono + Drizzle + better-sqlite3).
- `services/<name>/frontend` — frontend (React + Vite + Tailwind v4 + TanStack Query), built to `frontend/dist` and served by that service's own Hono app in production.
- `infra/` — systemd unit templates, Caddy site block, the VPS sync script. See `infra/README.md` for the full deployment story.
- `scripts/create-chamber.mjs` — scaffolds a new Chamber (`pnpm create-chamber <name> "<Display Name>" <port>`) from `scripts/create-chamber/template/`. See `docs/creating-a-chamber.md` for the full guide to building your own Chamber, including what the generator gives you vs. what you write by hand, and how to ship it to production.

**Per-frontend duplication is intentional in a few specific places**, not an oversight: `Layout.tsx`, `main.tsx`, `App.tsx`, `remote.tsx`, `src/feedRules.ts`, and `frontend/src/views/*.tsx` are deliberately small per-Chamber files (routing/copy/what's urgent is genuinely Chamber-specific) rather than another shared abstraction — don't try to collapse these into `chamber-kit`/`congress-ui` further. Everything that *was* pure copy-paste (icons, DB/env/MCP/registration boilerplate, the exhibits/settings/route-mounting pattern) has already been factored out; if you find yourself copying a whole file between two Chambers unchanged, that's a signal something belongs in one of the shared packages instead.

### The Chamber contract

Every Chamber implements the same contract (defined in `docs/congress-project-brief.md` section 4, scaffolded by `chamber-kit`):

- `GET /manifest` — self-description (name, routes, apiBase, mcpUrl, healthUrl, views, exhibitTypes, events).
- `GET /health` — liveness, used by Congress's heartbeat sweep.
- Exhibit editor routes (no list pages - a Chamber's index route redirects home unless it *is* a view, like Calendar's Timeline), an optional settings panel, and zero or more **views** — genuine screens, not lists of exhibits (see "Home" below).
- `GET /api/feed` (`chamber-kit`'s `mountFeedRoute`) — this Chamber's scored candidates for the home feed, built by pure rules in `src/feedRules.ts`.
- A REST API under `/api/*`.
- An MCP server at `/mcp` (Streamable HTTP transport, official `@modelcontextprotocol/sdk`), wrapping the same REST logic rather than touching the DB directly.

On boot, a Chamber calls `POST /congress/register` with its manifest (retrying with backoff if Congress isn't up yet — start order must never matter), then heartbeats `POST /congress/heartbeat` on an interval; Congress marks it `offline` in its registry if a heartbeat is missed past a threshold. Registration/heartbeat/exhibit-sync calls are authenticated with a shared `CONGRESS_INTERNAL_TOKEN` header (`requireInternalToken` in `services/congress/src/auth.ts`) — this is a "stop stray local processes" gate, not real auth. Congress itself is the registry owner, not a registrant — it never calls these on itself. (Congress's own API lives under `/congress/*` — a Chamber's own proxied frontend lives under `/<chamberName>/*`, so the two never collide.)

Each service owns exactly one SQLite file, opened only by its own process. Cross-Chamber data access always goes over HTTP through the owning Chamber's own API — never a shared DB, never one service importing another's Drizzle schema.

### Gateway

Congress is the only service Caddy ever points at. Its `gateway.ts` proxies `/api/:chamber/*` (session-gated) to that Chamber's registered `apiBase`, and proxies each Chamber's frontend through at `/<chamberName>/*`, e.g. Notes at `/notes/*`. No Chamber port is reachable from outside Congress's own process — a Chamber is only ever hit directly in dev, or by Congress itself in production. Congress's own frontend serves its home screen directly at `/`, plus `/search`, `/notifications`, `/settings`, `/chat` and `/view/:chamber/:viewId` (no Chamber involved, so they work with none registered); those names are reserved (`RESERVED_CHAMBER_NAMES` — registering a Chamber by one is refused) and the service worker serves them from the cached shell. The old `/capitol/*` URL redirects to `/` — see `services/congress/frontend/src/App.tsx`.

### Shell-hosted Chamber navigation

Congress's frontend is a persistent shell: navigating to a Chamber, or between Chambers, never does a full page load — Congress's `ChamberHost` (`services/congress/frontend/src/components/ChamberHost.tsx`) dynamically `import()`s that Chamber's own build as a real ES module and mounts it directly into Congress's existing React tree and Router, instead of the browser following a link to `/<chamberName>/*`. This layers on top of the "fully separate process" independence above, not a replacement for it — a Chamber still owns its build/port/DB/backend entirely; the only new coupling is Chamber → Congress (each Chamber emits one extra build artifact and agrees to a few shared conventions), which is deliberately looser than Chamber ↔ Chamber independence.

- Each Chamber's `frontend/vite.remote.config.ts` (`build:remote`) builds `frontend/src/remote.tsx` — mirrors `main.tsx` minus `StrictMode`/`createRoot`/`BrowserRouter` — into `remote-entry.js`/`remote-entry.css`, with `react`/`react-dom`/`react-router-dom`/`@tanstack/react-query` left external. Additive to `build:web`'s output (same `dist/`, run after it), not a replacement — standalone/dev access is unaffected.
- Congress's `frontend/vite.vendor.config.ts` (`build:vendor`) builds the one shared copy of those externalized packages, served at `/vendor/*.js` and wired into `index.html` via an import map — required so a dynamically-mounted Chamber shares React's live module state with the shell instead of crashing with "invalid hook call" from two separate copies of "the same" React.
- A Chamber's own components can't always tell whether they're rendered standalone (under their own `BrowserRouter basename="/<chamber>"`) or shell-hosted (nested under Congress's basename-less Router at `/:chamber/*`) — `useShellHosted()`/`resolveChamberPath()` (`packages/congress-ui/src/ShellHostContext.tsx`) is the one signal that tells them apart, used anywhere a Chamber writes an absolute-looking path (`ChamberPicker`, `ChamberHeader`'s `titleHref`, `navigateToExhibit`'s same-Chamber branch). It's a plain `window` flag, not React Context — `congress-ui` is source-only and recompiled independently into every bundle, so a Context object created in one bundle isn't recognized by `useContext` in another.
- A registered-but-actually-unreachable Chamber (stale heartbeat, a genuine bug in that Chamber's own code) is caught by an error boundary in `ChamberHost`, not left to blank the whole shell.
- `infra/deploy/build-artifacts.sh` runs `build:vendor`/`build:remote` alongside `build:web` for every service — both artifacts have to exist for shell-hosting to work in production.

### Home: feed, views and the shell

Congress's shell has one navigation: a tab bar — Home · Search · + · Chats · Notifications (`components/TabBar.tsx`; Settings is the gear on Home) — fixed to the bottom on a phone (it publishes `--mobile-nav-height`, which every bottom-docked element already offsets by) and a slim left rail on desktop (`--chamber-picker-width`). Chambers have **no navigation and no list pages of their own**: a Chamber page has a back button (`ChamberLayout` → `useBackNavigation`), and a Chamber's index route is either a real view (Calendar's Timeline, the Map) or `ChamberIndexRedirect` (home).

- **Home** (`pages/HomePage.tsx`): the "Ask Congress" composer (hands the message to `/chat`, which sends it once), the owner's pinned views (a "stories" row, `settings.pinnedViews`), then the **feed**: `GET /congress/feed` (`services/congress/src/feed.ts`) fans out to every active Chamber's `GET /api/feed`, merges and ranks the scored candidates (`rankFeed` — the one place a smarter ranker, e.g. Haiku, can later slot in) and resolves exhibits. **Every feed item shows its information inline**: an exhibit candidate carries a `preview` (title, ISO time the browser formats in the owner's zone, short fields, a plain-text excerpt — see `chamber-kit`'s `plainTextPreview`), and only views with a feed card appear. A bare "open X" row never belongs in the feed.
- **Views** (manifest `views`) are **only genuine screens** that can't be expressed as a list of exhibits — Calendar's Timeline and Week, the Map's today map and classify queue, Fitness's Health. A list of exhibits ("open tasks", "upcoming events") is never a view: those exhibits reach the feed through the Chamber's `feedRules` and Search on their own. A view has a `fullPath` (its full screen), and/or `card: true` with a card component in the Chamber's remote `views` export, rendered in Congress's own frame (`components/ViewSlot.tsx` — title, reason, open link, per-card error boundary, offline hatch).
- **Search** (`pages/SearchPage.tsx`) lists every view as a catalog when empty, plus recent exhibits; while typing, matching views and exhibits across every Chamber. **"+"** (`components/CreateSheet.tsx`) lists every active Chamber's `exhibitTypes` and opens that Chamber's own editor. **Notifications** is the Logs inbox as a page.

### Exhibits: the cross-Chamber reference/search system

An "Exhibit" is any addressable piece of content in any Chamber (`note-42`, `document-7`, `event-3:cal:evt123`, ...). This is the one piece of real cross-cutting product logic in the system, worth understanding before touching notes/calendar/documents content code:

- Every Chamber implements a small **content contract** (`GET /api/exhibits/search`, `POST /api/exhibits/resolve`) — see `packages/chamber-kit/src/exhibits.ts`'s `createTableBackedExhibits` for the pattern notes/documents both use (Calendar's exhibits are Google Calendar events, not a local table, so it implements the same contract by hand in `services/chamber-calendar/src/exhibits.ts` / `google/events.ts`).
- Congress's own SQLite DB (`services/congress/src/db/schema.ts`) keeps `exhibit_cache` and `exhibit_refs` — a cache of every known Exhibit's name/url and a reverse-reference graph, populated whenever a Chamber calls `POST /congress/exhibits/sync` after a create/update/delete. `services/congress/src/exhibits.ts` fans search/resolve calls out to every active Chamber in parallel.
- In note/document/event bodies, `[[exhibit:chamber:id|Label]]` tokens (`packages/congress-ui/src/token.ts`) render as clickable chips (`ExhibitChip`) via `ExhibitAnnotatedText`/`useResolvedExhibits`. An Exhibit's Connections panel — every other Exhibit it's connected to, undirected, with no differentiation of which side established the connection — is computed live from `exhibit_refs`, not stored redundantly.

Exhibit Sharing (granting outside, no-login access to an Exhibit and everything it recursively references) previously lived here as a Congress-owned feature. It was removed rather than relocated — no `shares` table, share token auth, public viewer, or per-exhibit Share button/badge exist in this codebase today. It may return later as its own Chamber; don't read its absence as an oversight.

### Events and Notifications

`services/congress/src/events.ts` is a generic, chamber-agnostic event *relay*, not a log — any Chamber can publish (`POST /congress/events/publish`, via `chamber-kit`'s `createPublishEvent`) and Congress immediately push-relays it to every currently-active Chamber whose own declared subscriptions match, POSTing to that Chamber's own `POST /api/events/receive` (mounted for free via `chamber-kit`'s `mountEventReceiveRoute`). Congress never inspects an event's `type`/`payload` at all, never stores a publish anywhere, and never falls back to a chamber polling for it — it's pure fan-out, the same spirit as `exhibit_cache`'s own push sync. A delivery to a briefly-unreachable Chamber (e.g. mid-deploy-restart) is retried with increasing delays (up to ~2 minutes total) rather than requeued durably; if Congress itself restarts mid-retry, or the Chamber stays down past the last attempt, that one delivery is silently dropped — the publishing Chamber never learns either way, same "best-effort, fire-and-forget" contract `createPublishEvent` already had. A Chamber's *subscriptions* — which event types it wants relayed (or `"*"` for all of them) — are dynamic, not part of its static manifest: computed fresh and carried on its normal heartbeat (an eager out-of-band heartbeat right after a rule/directive mutation propagates a changed subscription list immediately; the next regular heartbeat self-heals Congress's own copy after a restart either way). Congress's own filter is only ever a coarse per-chamber gate; a receiving Chamber still does its own precise per-rule matching (condition fields, etc.) inside its own `onEvent` handler. A Chamber may still optionally declare the event types it publishes in its manifest's `events` field (`manifestEventSchema`, just `type`/`label`/`description?`/`payloadFields?`) purely as a descriptive catalog for another Chamber's own trigger-event picker, not a subscription or a requirement to ever fire one.

What used to be a single Notifications Chamber has split into two, each independently receiving Congress's relayed events on its own subscription — neither depends on the other, they're just two consumers of the same generic relay:

**Logs** (core Congress: `services/congress/src/eventReceive.ts`, `eventSettings.ts`, `eventHistory.ts`, `notifications.ts`, `pushSubscriptions.ts`; UI under Settings → Logs plus the Notifications tab) is the sole owner of "what should the owner see" — the in-app inbox, Web Push subscriptions and delivery, and a durable history of events worth keeping. It matches incoming events against **event settings** — one auto-derived, never user-created/deleted row per known event type (`event_settings` table, kept current by `eventCatalogSync.ts`): `label`/`description`/`chamber` are a read-only cache of that event's own manifest catalog entry, while two independent action toggles — `recordToHistory` and `notify` (with its own push title/body/link, `{{payload.x}}`-interpolated) — are the owner's own editable configuration. A newly-discovered event type defaults to `recordToHistory: true, notify: false` — log everything, notify on nothing until the owner explicitly opts a given event type into pushing. A row with both off is simply a known-but-inert event type. `notify` still dedupes on a template key exactly like the old automations did (an inbox shows current state, so a still-true condition re-firing updates the existing notification rather than piling up duplicates); `recordToHistory` deliberately does not — the `event_history` table is genuinely append-only, since a history is supposed to show what actually happened over time, including repeats. Each history row's own retention is set per-event-type (`historyRetentionMs`, falling back to a 90-day default), independent of Congress's own much-shorter switch. There is still no way to retract a notification already pushed — the owner dismisses it from the inbox directly, same restraint as before. Because it lives inside Congress, `publishEvent` (`events.ts`) hands every event to `handleReceivedEvent` in-process — no subscription, no HTTP hop, no `getSubscriptions` — before relaying to the subscribing Chambers; `eventCatalogSync.ts` derives event settings from Congress's own registry directly. The inbox is the tab bar's Notifications page (its unread badge on the tab); per-event history lives on each event's Settings → Logs detail view.



Chambers with their own "check a condition, then notify" logic (`chamber-tasks`' due-date check, `chamber-calendar`'s upcoming-event check) publish domain events (`tasks.due_soon`, `tasks.overdue`, `tasks.due_cleared`, `calendar.event_starting_soon`) rather than pushing a notification directly — the *decision* of whether/what to do about a fired event lives in an editable log rule (or a tracked item Congress's AI watches), not in that Chamber's own committed TypeScript. `chamber-tasks` fires these at the exact instant a threshold is crossed via a self-rescheduling next-wake timer (a single `setTimeout` armed for the soonest upcoming due/overdue threshold across all open tasks, re-armed on every task mutation) rather than a fixed poll interval; `chamber-calendar` still polls Google Calendar itself every 5 minutes to *discover* events (an external data source with no push subscription wired up), but layers the same precise-timer treatment on top to *fire* `calendar.event_starting_soon` at the exact instant rather than only on the next poll tick. There is no other way for a notification to reach the inbox, or for an event to trigger a cross-Chamber action: a Chamber that wants something to happen publishes an event and has no idea whether — or how — anything responds to it.

### AI: a core Congress capability

Congress owns the system's one AI (`services/congress/src/ai/`). The retired Deputy Chamber's directives became Congress's own tracked items (see Memory below); `ai/legacyDirectivesImport.ts` and `ai/legacyImport.ts` are one-time importers that can go once they've run in production.

**Engine** (`engine.ts`): shells out to the `claude` CLI in print mode, streaming `--output-format stream-json` with `--include-partial-messages` (token deltas), `--allowedTools mcp__*` (only MCP tools, never Bash/files/web), the prompt over stdin. Every run is **isolated from the machine**: `--strict-mcp-config` with a generated config (the Chambers + Congress's own `/mcp`; empty for the gate), `--disable-slash-commands`, Congress's own `--system-prompt`, and a fixed empty cwd outside any repo (`aiWorkspaceDir`) so no CLAUDE.md, personal MCP servers or skills leak in — without it a trivial call wrote ~100k tokens of cache. The cwd must stay stable: the CLI files sessions by it, and chat `--resume`s. A parsed `"result"` event is the run's verdict; every run gets an `ai_runs` row (activity, cost, verdict) — the audit trail behind "Why?" and Settings → AI → Activity.

**Queue and guardrails** (`jobQueue.ts`, `runAi`): one concurrency-1 priority queue (chat/answers, then tracked-item checks, proactive runs, the gate); queued jobs can be removed and the running one aborted (child killed, 15-minute hard timeout). Before anything spawns: the pause switch, the daily `$` cap (auto-pauses), and — for runs Congress starts itself (`AUTONOMOUS_KINDS`) — the proactive on/off switch and its own daily budget. `GET /congress/ai/runs/stream` (SSE) carries the in-flight run (replayed to new clients), queue changes and `thread_updated`; `congress-ui`'s `aiStream.ts` shares one EventSource per bundle behind `useAiStream`/`useAiStreamEvents`/`useAiRunStream`.

**Chat** (`chat.ts`, `threads.ts`, frontend `src/chat/`): threads (`ai_threads`/`ai_messages`), each `--resume`ing its own CLI session (a missing session falls back to a fresh one given the thread's recent history). Posting returns at once with a `runId`; the thread's `pendingRunId` is what every client renders "working" from, so it survives refresh and navigation. Replies stream in and are stored with a `status` (`ok`/`error`/`refused`/`cancelled`). Each turn's prompt carries the exhibits the owner referenced (resolved) and any asks other runs posted since the owner last wrote. Exhibit tokens work both ways: the composer's `@` picker, and chips in replies (`congress-ui`'s `ChatMarkdown`); invented tokens are flattened to labels (`repairInventedTokens`).

**Asks** (`asks.ts`, MCP tools in `mcp/askTools.ts`): the AI reaches the owner with `send_message` (optionally delayed = a reminder), `ask_question` (a form it designs, validated by `shared-types`' `askFieldSchema`/`answerSchemaFor` on both sides) and `propose_actions` (privileged changes — the AI judges what's privileged — which Congress executes *exactly as approved* over MCP, stopping at the first failure). Asks land in the calling run's thread (or one new AI thread per run), get an inbox entry, and push to devices only within `maxPushesPerDay` and outside quiet hours (`pushPolicy.ts`). Answers and decisions start a follow-up run in the thread. The Home "Congress asks" strip and one-tap answers read `GET /congress/ai/asks`.

**Memory** (`memory.ts`, `tracking.ts`, `recurrence.ts`, tools in `mcp/memoryTools.ts`, screen at `/chat/memory`): tracked items (`ai_tracking`: the AI's own notes, `nextCheckAt`, an optional code-advanced recurrence, watched events) and facts (`ai_facts`), both in every run's prompt. A self-rescheduling timer runs a background check when an item is due (stamped before the run, retried if refused), when an `immediate` watched event arrives (the AI's own events never count), or on "Check now". Checks reach the owner only through asks.

**Proactive** (`proactive.ts`, `meter.ts`): every published event (via `events.ts`' `onEventPublished`) goes into `ai_event_buffer` and a pure decaying meter (watched events weigh more; a heartbeat grows between looks; quiet hours hold it; a cooldown follows an "act"). Crossing it runs the gate — the cheap `gateModel` (Haiku), tool-less with `--json-schema` — on a digest of recent events, tracked items, open asks and upcoming feed items; only an "act" verdict starts a full proactive run. Both publish `congress.ai_proactive_run`.

**Chambers** can still call `POST /congress/ai/run` (internal token; `chamber-kit`'s `runCongressAi`) with their own prompt; nothing does today.

### Settings & theming

Chamber-wide (not per-device) preferences use a single-row settings table — `id` always `1`, select-then-insert-or-update — via `chamber-kit`'s `createSingleRowSettings`. Congress's dark mode setting is applied everywhere (including inside each Chamber's own frontend and every feed card, which mount as real components in the same document rather than iframes) through `useAppliedTheme`/`useCapitolSettings` in `congress-ui`, plus a pre-paint inline bootstrap script in every `frontend/index.html` that applies a cached `localStorage` theme value before first render to avoid a flash of the wrong theme. The home screen's pinned views live on the same Congress settings row (`pinnedViews`, edited in Settings → Home).

### Frontend: mobile-first, always

This is a PWA used on an iPhone first (see `docs/congress-project-brief.md`) — every UI change is designed for a mobile-sized viewport first, with a `@media (min-width: 641px)` override adding desktop chrome on top, never the other way around. Concretely:

- Any new floating/positioned element (a dropdown, popover, panel) defaults to `position: fixed` anchored to the viewport, not `position: absolute` anchored to whatever small trigger button opened it — a trigger near a screen edge is a bad anchor for a panel that can be taller or wider than the space next to it on a phone. `.exhibit-picker-dropdown`/`.exhibit-ref-add-popover`/`.notification-panel` in `packages/congress-ui/src/styles.css` are the reference idiom: fixed to the viewport with `left`/`right: 0.5rem` and `bottom: calc(var(--mobile-nav-height, 0px) + 0.5rem)` by default, switched to a conventional anchored dropdown only inside the desktop media query.
- Before calling any UI change done, actually load it in a browser at a mobile viewport width (~375px) — not just skim the CSS — and check the specific thing you touched still fits and works. A change that only gets checked at desktop width has not been verified.

## Deployment

Full details in `infra/README.md`. Key points to know before pushing to `main`:

- Deploy is push-based, driven by GitHub Actions (`.github/workflows/deploy.yml`), not a server-side poll — **there is no separate deploy step**, pushing to `main` is the deploy. CI builds and tests, then pushes the finished tree to the VPS (`178.105.180.7`) over rsync+SSH and tells it to install runtime deps and restart. The server itself never runs git or a build tool — see `infra/README.md`'s "Deploy: GitHub Actions → server" section for the full flow.
- Production ports differ from dev defaults: Congress `8000` (not `3000`, since that VPS runs other unrelated projects too), Notes `8011`, Calendar `8012`, Documents `8013`, Tasks `8014`, Map `8019`, Fitness `8020` — same as dev for the Chambers, different for Congress. Don't assume Congress is on `3000` when checking anything server-side.
