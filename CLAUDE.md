# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Congress is a personal, self-hosted productivity system for a single user, deployed at `congress.marinprusac.com`. It's a monorepo with one service and a few shared packages. The full design intent is in `docs/congress-project-brief.md`; read it for the "why" behind anything that looks unusual. Note that two things have changed since that brief was written: the brief specifies Tailscale-only private access, but the deployed system now uses public access gated by a master-password session cookie instead (see `infra/README.md`, "Access control"); and the brief describes independent Chamber services with one widget each in an iframe, but the system is now one service with a ranked "For You" home feed (the AI lives in the Chats tab) and no widgets or per-source navigation — see "Home: feed, views and the shell" below and `docs/writing-a-connector.md`. Trust `infra/README.md` and this file over the brief on deployment/access and homepage details respectively.

Three names are used consistently in code, folders, and package names:

- **Congress** — both the whole system and its one service: `services/congress` is session auth, the **type engine** (runtime exhibit types, records, search, bindings), the **connectors** (hand-written sync code: Google Calendar, Gmail, Hevy, Apple Health, Traccar, WhatsApp), Congress's own **views** (Calendar, Health, Map, WhatsApp chats), the **home screen** (the feed, pinned views, Search, "+"), the **event log/notification center** (see "Events and Notifications"), the system's one **AI** (see "AI"), and the PWA shell. One process (`congress-core`), and the only thing Caddy ever points at.
- **Capitol** and **Logs** no longer exist as Chambers — they were folded into Congress as core features (the home screen at `/`, the Notifications tab, event settings/history under Settings → Logs). The name "Capitol" survives only in a few legacy identifiers (`CapitolMark`, `useCapitolSettings`, `capitolSettingsSchema`). `services/congress/src/legacyImport.ts` is a one-time importer of the old Logs SQLite file (and `ai/legacyImport.ts` of Deputy's old AI settings row); both can be deleted once they have run in production.
- **Chamber** — retired. Congress used to load independent modules called Chambers; Notes, Tasks, Documents, Calendar, Mail, Fitness, Map and WhatsApp all became premade types plus connectors and views (phase 7, finished 2026-10-01), and the machinery that ran them (chamber-kit, the registry, gateway dispatch, `ChamberHost`, remote builds, `create-chamber`) is gone. The name survives in identifiers (`ChamberHeader`, `ChamberMark`, `chamber` fields that now mean an exhibit's source namespace such as `e`) and in the folder `services/chamber-whatsapp`, which holds only the Go reader daemon. To add something new: a type (builder mode or a premade), a connector, a view; see `docs/writing-a-connector.md`.

## Commands

There's no root-level dev/build orchestration (no turbo/nx); the app is one service, `congress`, plus the shared `packages/*`.

```bash
pnpm install                                   # once, from repo root

pnpm --filter congress dev:server              # backend, watch mode
pnpm --filter congress dev:web                 # frontend, Vite dev server (proxies the API to :3000)
pnpm --filter congress build:web               # frontend production build -> frontend/dist
pnpm --filter congress typecheck               # tsc --noEmit, server + frontend tsconfig

pnpm -r typecheck                              # typecheck every package/service — run this after any change
pnpm typecheck                                 # the above, plus the root tests/ directory

pnpm test                                      # vitest, whole monorepo — run this after any change
pnpm test services/congress/src/typeEngine   # any path fragment filters
pnpm test:watch                                # vitest in watch mode

pnpm --filter congress db:generate               # after editing src/db/schema.ts -> drizzle-kit generate (each connector DB has its own drizzle.<name>.config.ts)
pnpm --filter congress db:migrate                # apply migrations locally (also auto-applied on boot)
```

There is no lint config in this repo — `pnpm typecheck` and `pnpm test` are the two automated checks, and both are expected to pass cleanly before committing.

**A new feature ships with tests for it, in the same change** — not as a follow-up, and not only when asked. This matters more here than in most repos because pushing to `main` is the deploy (see Deployment below): there is no stage between a regression and production. Aim them at stateful and cross-service logic — state machines, caches, matching rules, auth wiring — rather than plain CRUD route handlers, which `strict` + `noUncheckedIndexedAccess` already protect well; the point is to cover what typecheck cannot reach, not to hit every line.

Tests are Vitest, configured once at the root (`vitest.config.mts`) rather than per service, and live beside the code they cover as `src/**/*.test.ts` (plus `tests/` at the root for cross-service checks like the migration smoke test). They run in a Node environment only — there is no jsdom setup, so frontend coverage is limited to `congress-ui`'s pure string helpers, not component rendering. Shared helpers live in `packages/test-support` (`@congress/test-support`) — a workspace package rather than a plain folder, so each service's own `typecheck` (which pins `rootDir` to its own `src/`) can still see them. A few things make this work and are worth knowing before adding a suite:

- Congress opens its SQLite handle and parses its env **at module load** (`src/db/client.ts`, `src/env.ts`). `packages/test-support/src/env.ts` is a Vitest `setupFile`, so it runs before any of that and points `DB_PATH` at a fresh temp file — one per test file, since Vitest gives each test file its own module registry. A test that needs several databases in one file resets with `vi.resetModules()` after moving `process.env.DB_PATH`.
- `runMigrations()`'s default migrations path is relative to the process cwd (the repo root under Vitest), so tests pass an absolute one via `migrationsDir(<service>)`.
- Connector tests run against fake upstreams (`gmail/fakeGmail.ts`, a unix-socket fake reader for WhatsApp, a fake Hevy) and exhibit-source tests register in-process sources; nothing reaches a real service.
- When the logic worth testing is module-private, adding an `export` to it is fine, and pulling a cluster of it into a leaf module next to its caller (the way `geo.ts` and `annotationMatching.ts` sit beside the location connector's `tracking.ts`/`reprocess.ts`) is better still — both are established here, not a workaround.

`infra/deploy/pre-push-hook-checks` enforces both checks before a push, blocking it on failure for fast local feedback. Install it with `cp infra/deploy/pre-push-hook-checks .git/hooks/pre-push && chmod +x .git/hooks/pre-push`. The same two checks also gate the actual deploy in CI (see Deployment below) — a push that skips the local hook (`--no-verify`) still can't reach production without passing them.

The frontend dev server proxies `/api`, `/auth`, `/congress` and `/mcp` to Congress's dev port (`3000`) — see `frontend/vite.config.ts`. The built frontend is one bundle (no import map, no remote entries) served by the backend from `frontend/dist`.

## Architecture

### Repo shape

- `packages/shared-types` — zod schemas and DTOs shared across every service (manifest shape, exhibit search/resolve contracts, settings types). Types and schemas only, never logic — kept small enough that a Chamber written in another language could reimplement its shape from the JSON Schema alone.
- `services/congress/src/kit/` — the small backend helpers the code shares: `createDb`/`createLazyDb`, `loadEnv`, `createMcpApp`/`mcpTextResult`/`callChamberTool`, `createSingleRowSettings`, wikilink parsing, `interpolate`, `plainTextPreview`/`closeness`, `scoreExhibitMatch`, static serving and the Google error classes. (They lived in `packages/chamber-kit` until phase 7e.)
- `packages/congress-ui` — **frontend** components/hooks: `ChamberLayout`/`ChamberHeader` (page chrome), the Exhibit chip/picker/annotated-text system, dark mode (`useAppliedTheme`), stack navigation (`StackLink`/`useStackNav`/`useBackNavigation`), motion, `ChamberMarks` icons. Source-only workspace package, consumed via `@congress/congress-ui` (components) and `@congress/congress-ui/styles.css`.
- `services/congress/src` — backend (Hono + Drizzle + better-sqlite3); `services/congress/frontend` — frontend (React + Vite + Tailwind v4 + TanStack Query), built to `frontend/dist`.
- `infra/` — the one systemd unit (`congress-core`), Caddy site block, the deploy scripts. See `infra/README.md` for the full deployment story.
- `docs/writing-a-connector.md` — how to add a connector, a premade type or a view.

### Server shape

Congress is the only service Caddy points at (`server.ts`): `/auth`; `/congress/*` (session-gated: settings, feed, records and types, connectors, AI, notifications; a connector's setup-panel API is `/congress/connectors/<name>/*` and its unauthenticated webhooks `/hook/*`); `/mcp`, `/mcp/types` and `/mcp/builder` (the AI's tools, gated by the internal token `CONGRESS_INTERNAL_TOKEN`); the Health Auto Export Shortcut's old URL `/api/fitness/health/ingest`; view icons at `/congress/chambers/:name/icon` (`CORE_ICONS` in `gateway.ts`); then the SPA from `frontend/dist` (`kit/static.ts`). Any other `/api/*` is a JSON 404.

The frontend is one bundle. Views are ordinary routes in `App.tsx`, and Congress's own view cards (`views/coreViews.ts`) are real components in the same document. Old Chamber URLs (`/mail/...`, `/notes/...`) are redirects there. The service worker's shell allowlist (`sw.ts`) must list every top-level path `App.tsx` serves.


### Home: feed, views and the shell

Congress's shell has one navigation: a tab bar — Home · Search · + · Chats · Notifications (`components/TabBar.tsx`; Settings is the gear on Home) — fixed to the bottom on a phone (it publishes `--mobile-nav-height`, which every bottom-docked element already offsets by) and a slim left rail on desktop (`--chamber-picker-width`). Views have **no navigation of their own**: a page has a back button (`ChamberLayout` → `useBackNavigation`).

- **Home** (`pages/HomePage.tsx`): the "Congress asks" strip, the owner's pinned views (a "stories" row, `settings.pinnedViews`), then the **feed**: `GET /congress/feed` (`services/congress/src/feed.ts`) gathers every source's scored candidates (the type engine's feed rules, connectors' `feed()`), merges and ranks them (`rankFeed` — the one place a smarter ranker, e.g. Haiku, can later slot in) and resolves exhibits. **Every feed item shows its information inline**: a record candidate carries a `preview` (title, ISO time the browser formats in the owner's zone, short fields, a plain-text excerpt — see `kit/feedText.ts`'s `plainTextPreview`), and only views with a feed card appear. A bare "open X" row never belongs in the feed.
- **Views** (`views/coreViews.ts`) are **only genuine screens** that can't be expressed as a list of records — the calendar's Timeline and Week, the Map's today map and classify queue, Health, the WhatsApp chat list. A list of records ("open tasks", "upcoming events") is never a view: those reach the feed through the type's feed rules and Search on their own. A view has a `fullPath` (its full screen), and/or `card: true` with a `Card` component rendered in Congress's own frame (`components/ViewSlot.tsx` — title, reason, open link, per-card error boundary). A source shows once its type is in use.
- **Search** (`pages/SearchPage.tsx`) lists every view as a catalog when empty, plus recent records; while typing, matching views and records. **"+"** (`components/CreateSheet.tsx`) lists every type the owner can create by hand and opens its editor. **Notifications** is the Logs inbox as a page.

### Stack navigation

Navigation is a stack of pages **per tab** (Home, Search, Chats, Notifications), with browser history always equal to the active tab's stack — so browser back, the iOS edge-swipe and every in-app back button do the same thing. The model is pure (`congress-ui`'s `navStack.ts`); `navEngine.ts` drives the router and history from it; the shell mounts `StackNavigator` once and publishes the engine on `window` (not Context, for the same reason as `useShellHosted`), so a Chamber bundle reaches the same instance.

- **Push** (`StackLink`, `useStackNav().push`) drills in on the current tab; **pop** (`useStackNav().pop`, `useBackNavigation`) goes back to the page underneath, or the tab's root when there's none. After a Delete/Cancel a page pops — it never navigates "home", which would stack a second root and leave the deleted page one back.
- Chat pages (`/chat/*`) and the four tab roots always belong to their own tab: pushing one from elsewhere switches tabs (Home's "Congress asks" → `[/chat, /chat/5]`). Anything else (a Chamber page, a view, Settings) belongs to the tab it was pushed from.
- A tab tap (`selectNavTab`) restores that tab's stack by stepping history back to the current stack's root and rewriting it as the target's; tapping the active tab pops it to its root. Stacks and scroll positions persist in `sessionStorage` across reloads.
- A cold load of a deep link (bookmark, notification tap) gets its tab's root underneath (`planColdStart`); a notification's tab rides on `?navtab=` and is stripped. With the app open, `sw.ts` posts the URL to the page instead of reloading it (`openInTab`).
- A plain `<Link>`/`navigate()` still works — `StackNavigator` reconciles every committed location — but goes without the push/pop transition, so new code uses `StackLink`/`useStackNav`. A `replace` is fine for swapping the top page (after a create, Calendar's Timeline/Week switch).

### Runtime exhibit types (the type engine)

The shape: what used to be Chambers is **exhibit types** defined at runtime (each a real SQLite table with real columns, rendered generically by Congress), hand-written **connectors** wired into those types, hand-written **views**, and the AI. Built in phases 1-7 (the engine, Note, Task and Document, builder mode, relations and Person, the connector contract with Google Calendar, bindings and Event, then Mail, Fitness, Map and WhatsApp, and finally removing the Chamber machinery). Code lives in `services/congress/src/typeEngine/`:

- **Storage**: `exhibits.sqlite3` (`EXHIBITS_DB_PATH`), separate from Congress's core DB. Meta tables (`types`, `type_versions`, `records`, `record_refs`, `legacy_aliases`, `imports`) are drizzle-managed with their own migrations folder; each type's table (`x_<slug>`, plus `j_*` join tables for to-many relations) is created at runtime with raw better-sqlite3. Record ids are opaque ULIDs in one exhibit namespace, `e` (`[[exhibit:e:<ulid>|Title]]`, URL `/e/<ulid>`).
- **Definitions change only through operations** (`operations.ts`, pure; `Operation` in shared-types): field ids and columns are fixed at creation, so renames and retires cost no SQL. `planner.ts` (pure) diffs two definitions into SQL - ALTER, index diffs, or a table rebuild through the `te_cast` SQL function (`casts.ts`) for kind changes. `store.ts` publishes a change and its version row in one transaction (a snapshot first if a rebuild is planned); `rollback` restores an earlier definition with newer fields kept, retired. Removing a field retires it; nothing drops data.
- **Field kinds**: text, richtext, boolean, datetime (epoch ms), `date` (a calendar day, `YYYY-MM-DD`; its boundaries are in the owner's zone, `zone.ts` - AI settings' zone, else `OWNER_TIMEZONE`), number, enum, relation, and `file`. A `readonly` field is engine-written only (never in input).
- **Files** (`files.ts`): uploads stream raw to `PUT /congress/files` into `EXHIBIT_FILES_DIR/<id>` (a `files` row with its sha256; `MAX_UPLOAD_BYTES`), are served ranged at `GET /congress/files/:id` (inline only for inert types, `nosniff`), and a file field holds the id. Files are immutable; one no record uses is orphaned and deleted 14 days later (the backup window, so a restored snapshot finds its files). The AI uploads with `upload_file`.
- **Premade types** (`premade/`) are ordered op batches applied once each at boot, like migrations; one that no longer applies (the owner changed the type) marks it `forked`. Note, Task, Document and Person.
- **Relations**: a relation field names its target type by slug (it must exist; target and `many` are fixed once added, and a linked-to type keeps its slug). Linked ids must be records of the target. Deleting a record clears every link to it. `relatedRecords` (`GET /congress/records/:id/related`) is the reverse view, shown as a record page's Related section (and left out of Connections).
- **Keys and `lookupOrCreate`** (`keys.ts`, `lookups.ts`): a text field with `key: "email" | "phone"` holds one value per line, each normalized into `record_keys` and unique per type. `lookupOrCreate` finds a record by any key, or creates one when the type's `autoCreate` policy (`never` / `corresponded` / `any`) trusts the evidence (`owner` always; Person is `corresponded`). Connector bindings call it in-process; the AI gets `find_or_create_<slug>`.
- **Records** (`records.ts`): generic CRUD; every write re-syncs `exhibit_cache`/`exhibit_refs` (richtext tokens, relation values, manual refs) and publishes `<eventPrefix>.created|updated|deleted` from source `types`. A toggle action can also publish on/off events and stamp a datetime whenever its boolean flips, by any writer (Task: `completed`/`reopened`, `completed_at`). `feedRules.ts` compiles a type's declarative feed rules. `exhibitSources.ts` (core) lets `exhibits.ts`/`feed.ts` serve in-process namespaces next to Chambers.
- **Time triggers** (`triggers.ts`, op `set_time_triggers`): a ladder of steps relative to a date/datetime field, with `and` conditions. A record's state is the latest step reached (kept in `record_trigger_state`); a change publishes that step's event and falling out of every step publishes the clear event (Task: `due_soon` 24h before its day ends, `overdue`, `due_cleared`). One next-wake timer covers every type, and each record write re-evaluates that record at once.
- **Surfaces**: REST at `/congress/types`, `/congress/records` and `/congress/files`, the `/mcp/types` MCP server (per-type list/search/get/create/update/delete, `find_or_create_*` for types with keys, plus `upload_file`, rebuilt per request), and the frontend's `records/RecordPage.tsx` at `/e/:id` and `/e/new/:type` (a draft is created once its required fields are set).
- **Legacy ids**: a Chamber's import writes `legacy_aliases`, so its old ids (`note-42`, `task-7`, `document-3`) keep resolving, syncing and connecting without other text being rewritten, and old URLs redirect (`records/LegacyRedirect.tsx`). Notes (93) and then Tasks (41) and Documents (13) were imported in production on 2026-09-30, and the importers removed; see git history (`typeEngine/legacy/`, with its `import:legacy` dry run) for the pattern when migrating the next Chamber. The owner's 23 person notes became Person records under the same ids (2026-09-30; importer removed, see git history).
- **Backups**: `backups.ts` takes a nightly `VACUUM INTO` of both DBs into `data/backups/` (14 days).
- **Builder mode** (how definitions change at runtime): the AI never edits a type directly.
  - **Grant:** any run may call `request_builder_mode` (a `builder_request` ask). The owner grants it for 15 min, 1 h or 4 h in that thread (`ai_builder_grants`, `ai/builder.ts`).
  - **Tools:** only a granted thread's runs get the `/mcp/builder` server (`mcp/builderTools.ts`), and every call re-checks the grant.
  - **Drafts:** ops (or a rollback) collect in `type_drafts` (`drafts.ts`) against a base version. `previewPublish` shows exactly what publishing would do (read-only preflight counts, the same code `commit` runs), and `diff.ts` describes it in sentences.
  - **Publishing:** each publish is its own `type_publish` ask, frozen by a hash of the draft. Approval publishes exactly that (`publishDraft`), and a draft that changed or went stale fails instead. A publish to a premade type marks it forked.
  - **Settings → Types** is read-only: types plus version history with diffs.
- **Connectors** (`services/congress/src/connectors/`): hand-written sync code with its own cache DB (`CONNECTORS_DATA_DIR/<name>.sqlite3`), declared with `defineConnector` (`contract.ts`): a source schema (kinds, fields, email keys, per-record **facts** such as `editable`/`canRsvp`), `sync` (pull, run by `registry.ts`'s scheduler), `read`, optional `push` (create/update/delete/`act`), a setup-panel Hono app at `/congress/connectors/<name>/*`, and `onEvent` for `google.account_*`. A connector never writes type records; it emits source changes (`runtime.ts`'s `onSourceChange`) that bindings pull in, and resolves people through `ctx.people.resolve` (`lookupOrCreate` on Person). Its `googleScopes` join the Google connect union. Setup lives in Settings → Connectors (`frontend/src/connectors/panels.tsx`).
  - **Bindings** (`typeEngine/bindings/`, phase 6) wire a connector's source kind into a type, as part of its definition (ops `set_binding`/`remove_binding`, checked against the running connector's schema at publish; premades skip that check).
    - **Fields:** `sync` fields are pulled and pushed back; `pull` fields are read-only on bound records; unbound fields stay local. Unmapped source values are read live (`withBinding` → `RecordDto.binding`).
    - **Pull:** a pull applies only what the source changed since the record's shadow (`binding_shadows`), so pending local edits and push echoes survive. Rich text keeps its chips while its plain projection still matches. The first pull is a quiet backfill (no events; time triggers seed silently). Records outlive the source's window; only an emitted delete removes one.
    - **Push:** owner/AI edits push through `binding_outbox` (retry with backoff; a `ConnectorRefusedError` reverts to the source and shows as failed).
      - Changing the `create` target field creates, moves (same record id) or detaches.
      - Source changes are held while a create is in flight.
    - **Guard:** `beforeRecordWrite` refuses locked fields (`lock` fact false, or the source no longer has it) and `delete: "never"`. Actions (`POST /congress/records/:id/actions/:action`) call `push.act` when their `when`/`unless` facts hold.
  - **Event** (premade) replaced the Calendar Chamber (2026-09-30: local events, "not attending" as Hide, rich text, links, old `event-…` ids as aliases, event settings and pins; the importer and its `import:calendar` dry run are in git history). A hidden type publishes no events. Its binding syncs title/time/place/description/calendar, pulls your response and linked People, locks others' invitations (`editable` fact) and offers Accept/Maybe/Decline (real RSVPs); Hide is a local toggle. The connector's times are instants (all-day = midnight in the owner's zone, end exclusive); changing the calendar field creates/moves/detaches.
  - **Calendar views** (`frontend/src/views/calendar/`): Timeline at `/events` and Week at `/events/week`, hand-written over Event records (`GET /congress/records?type=event&from=&to=`), with calendar colors and account problems from the connector's status. `views/coreViews.ts` lists Congress's own views next to Chambers' (Search, pinned views); they appear once their type is visible.
  - **Live content and search** (phase 7): a connector may offer `read.detail` (live content for a record, e.g. a thread's bodies: `GET /congress/records/:id/live`, the AI's `read_<slug>`), `read.search` (the whole source, `search_all_<plural>`) and `read.fetch` (one item into its cache, so `materialize` makes it a record on demand). It publishes its own events with `ctx.publish` (declared in `events`, so Settings → Logs lists them), adds AI tools with `tools`, and `emitChange(..., quiet)` pulls a backfill without events. A type whose bindings can't create (`canCreate`) only gets records from its source.
  - **Gmail** (`gmail/`) is the Email type's source and replaced the Mail Chamber (2026-09-30; its `import:mail` dry run and importer are in git history): one cached row per thread (never windowed; 30-day backfill, then Gmail history, each touched thread re-read live), bodies/HTML/attachments live (`frontend/src/connectors/live/GmailThread.tsx`, a sandboxed CSP-locked iframe with remote images blocked until tapped), Mark read (on open) as its only write, never send or delete. It publishes `mail.received` (Primary only unless its panel says every category) and creates People only from the **To** of mail the owner sent; everyone else just links. Old `thread-<acct>:<thread>` ids are aliases and `/mail/t/...` redirects.
  - **Hevy** and **Apple Health** (`hevy/`, `health/`) replaced the Fitness Chamber (2026-09-30; old `workout-<id>`/`routine-<hevyId>` ids are aliases, `/fitness/...` redirects; the importer and its `import:fitness` dry run are in git history). Hevy fills Workout (pull-only; sets and 1RMs read live, `frontend/src/connectors/live/HevyWorkout.tsx`) and Routine (a rename goes back to Hevy; exercises are edited in `HevyRoutine.tsx` / `hevy_set_routine_exercises`; a new one is made at `/e/new/routine` once it has an exercise, and never retried, since Hevy can't delete a routine). Health is a time series (`read.series`), never records, filled by Health Auto Export through the unauthenticated `hooks()` webhook (the Shortcut's old `/api/fitness/health/ingest` reaches it via `callHook`), drawn by the core Health view (`/fitness/health`, a feed card through the connector's `feed()`).
  - **Location** (`location/`) replaced the Map Chamber (2026-10-01; old `place-<id>` ids are aliases and `/map/...` redirects; the importer and its `import:map` dry run are in git history). The Map is Congress's own views: `/map` (the day's places and trips, Leaflet; the feed card "Today") and `/map/pending` (stops to classify: a new place is a Place record made there, whose rebuild confirms the stop), in `frontend/src/views/map/`; Traccar and the tunables live in its Settings → Connectors panel. It is the Map Chamber's tracking engine (positions kept forever; visits and trips rebuilt from them, the owner's classifications carried across) reading the owner's **Place** records (hidden until then) through `ctx.records.list` and `onRecordChange`: a Place made, moved or deleted rebuilds that stretch of history. Place's latitude/longitude/radius are plain number fields paired into one map picker by `set_map_point` (`layout.mapPoint`). Its feed (`feed()`: groups per source) is today's map card under "map" and "You're here" as a Place record under "e".
  - **WhatsApp** (`whatsapp/`) replaced the WhatsApp Chamber (2026-10-01; there was nothing to import, `/whatsapp/...` URLs are unchanged, the Chats view keeps its pin): wraps the wa-reader socket (`readerClient.ts`, whose only POSTs are pairing and the local mark-read; `readonly.test.ts` keeps it so). One Chat record per chat the reader knows, synced every 2 minutes and pulled quietly (chat activity is too frequent to announce); messages stay in the reader. People by phone (`people.find/resolve` take `{ email?, phone? }`): only a 1:1 chat the owner wrote in at least five times (of its last 100 messages) may create one (`createPeople`, on by default, a checkbox in its Settings → Connectors panel, which also holds the QR pairing). The views are Congress's own (`frontend/src/views/whatsapp/`: `/whatsapp` the chat list, `/whatsapp/c/:jid` a chat, read-only, marking read locally when seen) and a Chat record shows its newest messages live (`connectors/live/WhatsappChat.tsx`). AI tools `whatsapp_*`.
  - **Google Calendar** (`googleCalendar/`) is the Event type's source. It caches selected calendars over ±180 days (sync tokens, 410 → full resync), with every guest. Guests never create People (being on an invitation isn't contact): each sync links unlinked guests to existing People by email (`ctx.people.find`). A Person is only ever created from **direct contact** - the owner or the AI, or later a connector that sees the owner wrote to someone themselves (Mail, WhatsApp; evidence `corresponded`). Event's binding pushes edits, moves and answers through it; the AI's calendar tools are the generic `/mcp/types` ones (`list_events` with `from`/`to`, `decline_event`, ...).

### Exhibits: references and search

An "exhibit" is any addressable piece of content (today: every record, namespace `e`). `services/congress/src/exhibitSources.ts` lets a namespace be served in-process (`registerLocalSource`: `search`, `resolve`, `chip`, manual refs, `feedCandidates`); the type engine registers `e` (`typeEngine/source.ts`), and `exhibits.ts`' `searchExhibits`/`resolveExhibits`/`getExhibitChip`/`getConnections` read only those sources.

- Congress's own SQLite DB keeps `exhibit_cache` and `exhibit_refs` — a cache of every known exhibit's name/url and a reverse-reference graph, written by `syncExhibit` on every record write.
- In bodies, `[[exhibit:e:<id>|Label]]` tokens (`packages/congress-ui/src/token.ts`) render as clickable chips (`ExhibitChip`) via `ExhibitAnnotatedText`/`useResolvedExhibits`. A record's Connections panel — every other exhibit it's connected to, undirected — is computed live from `exhibit_refs`, not stored redundantly.

Exhibit Sharing (granting outside, no-login access to an exhibit and everything it recursively references) previously lived here as a Congress-owned feature. It was removed rather than relocated — no `shares` table, share token auth, public viewer, or per-exhibit Share button/badge exist in this codebase today. It may return later; don't read its absence as an oversight.


### Events and Notifications

`services/congress/src/events.ts` is a small in-process bus, not a log — anything (the type engine, a connector via `ctx.publish`, the AI) calls `publishEvent`, and it hands the event to the AI's observers (`onEventPublished`) and to Congress's own log rules (`eventReceive.ts`), never storing it itself. A throwing handler is logged and never reaches the publisher. Event types are declared in a catalog (a type's `eventPrefix`, a connector's `events`, and `CONGRESS_SYNTHETIC_EVENTS`) which `eventCatalogSync.ts` turns into settings rows. Connectors also get every event through their own `onEvent` (Gmail and Google Calendar forget a disconnected account's data on `google.account_disconnected`).

Log rules (below) are the one consumer of the relayed events that decides what the owner sees:

**Logs** (core Congress: `services/congress/src/eventReceive.ts`, `eventSettings.ts`, `eventHistory.ts`, `notifications.ts`, `pushSubscriptions.ts`; UI under Settings → Logs plus the Notifications tab) is the sole owner of "what should the owner see" — the in-app inbox, Web Push subscriptions and delivery, and a durable history of events worth keeping. It matches incoming events against **event settings** — one auto-derived, never user-created/deleted row per known event type (`event_settings` table, kept current by `eventCatalogSync.ts`): `label`/`description`/`chamber` are a read-only cache of that event's own manifest catalog entry, while two independent action toggles — `recordToHistory` and `notify` (with its own push title/body/link, `{{payload.x}}`-interpolated) — are the owner's own editable configuration. A newly-discovered event type defaults to `recordToHistory: true, notify: false` — log everything, notify on nothing until the owner explicitly opts a given event type into pushing. A row with both off is simply a known-but-inert event type. `notify` still dedupes on a template key exactly like the old automations did (an inbox shows current state, so a still-true condition re-firing updates the existing notification rather than piling up duplicates); `recordToHistory` deliberately does not — the `event_history` table is genuinely append-only, since a history is supposed to show what actually happened over time, including repeats. Each history row's own retention is set per-event-type (`historyRetentionMs`, falling back to a 90-day default), independent of Congress's own much-shorter switch. There is still no way to retract a notification already pushed — the owner dismisses it from the inbox directly, same restraint as before. Because it lives inside Congress, `publishEvent` (`events.ts`) hands every event to `handleReceivedEvent` in-process — no subscription, no HTTP hop, no `getSubscriptions` — before relaying to any subscribing Chambers; `eventCatalogSync.ts` derives event settings from Congress's own registry directly. The inbox is the tab bar's Notifications page (its unread badge on the tab); per-event history lives on each event's Settings → Logs detail view.



"Check a condition, then notify" logic (a Task's due date, an Event about to start) publishes domain events (`task.due_soon`, `task.overdue`, `task.due_cleared`, `event.starting_soon`) rather than pushing a notification directly — the *decision* of whether/what to do about a fired event lives in an editable log rule (or a tracked item Congress's AI watches), not in committed TypeScript. Task's and Event's come from the type engine's time-trigger ladders (see "Runtime exhibit types"), which fire at the exact instant a threshold is crossed via one self-rescheduling next-wake timer (a single `setTimeout` armed for the soonest upcoming step across every type, re-armed on every record write) rather than a fixed poll interval (a new ladder records past steps silently, and a "before" step reached after its moment isn't announced); the Google Calendar connector polls Google to *discover* events. There is no other way for a notification to reach the inbox, or for an event to trigger a cross-Chamber action: a Chamber that wants something to happen publishes an event and has no idea whether — or how — anything responds to it.

### AI: a core Congress capability

Congress owns the system's one AI (`services/congress/src/ai/`). The retired Deputy Chamber's directives became Congress's own tracked items (see Memory below); `ai/legacyDirectivesImport.ts` and `ai/legacyImport.ts` are one-time importers that can go once they've run in production.

**Engine** (`engine.ts`): shells out to the `claude` CLI in print mode, streaming `--output-format stream-json` with `--include-partial-messages` (token deltas), `--allowedTools mcp__*` (only MCP tools, never Bash/files/web), the prompt over stdin. Every run is **isolated from the machine**: `--strict-mcp-config` with a generated config (Congress's own `/mcp`, `/mcp/types`; empty for the gate), `--disable-slash-commands`, Congress's own `--system-prompt`, and a fixed empty cwd outside any repo (`aiWorkspaceDir`) so no CLAUDE.md, personal MCP servers or skills leak in — without it a trivial call wrote ~100k tokens of cache. The cwd must stay stable: the CLI files sessions by it, and chat `--resume`s. A parsed `"result"` event is the run's verdict; every run gets an `ai_runs` row (activity, cost, verdict) — the audit trail behind "Why?" and Settings → AI → Activity.

**Queue and guardrails** (`jobQueue.ts`, `runAi`): one concurrency-1 priority queue (chat/answers, then tracked-item checks, proactive runs, the gate); queued jobs can be removed and the running one aborted (child killed, 15-minute hard timeout). Before anything spawns: the pause switch, the daily `$` cap (auto-pauses), and — for runs Congress starts itself (`AUTONOMOUS_KINDS`) — the proactive on/off switch and its own daily budget. `GET /congress/ai/runs/stream` (SSE) carries the in-flight run (replayed to new clients), queue changes and `thread_updated`; `congress-ui`'s `aiStream.ts` shares one EventSource per bundle behind `useAiStream`/`useAiStreamEvents`/`useAiRunStream`.

**Chat** (`chat.ts`, `threads.ts`, frontend `src/chat/`): threads (`ai_threads`/`ai_messages`), each `--resume`ing its own CLI session (a missing session falls back to a fresh one given the thread's recent history). Posting returns at once with a `runId`; the thread's `pendingRunId` is what every client renders "working" from, so it survives refresh and navigation. Replies stream in and are stored with a `status` (`ok`/`error`/`refused`/`cancelled`). Each turn's prompt carries the exhibits the owner referenced (resolved) and any asks other runs posted since the owner last wrote. Exhibit tokens work both ways: the composer's `@` picker, and chips in replies (`congress-ui`'s `ChatMarkdown`); invented tokens are flattened to labels (`repairInventedTokens`).

**Asks** (`asks.ts`, MCP tools in `mcp/askTools.ts`): the AI reaches the owner with `send_message` (optionally delayed = a reminder), `ask_question` (a form it designs, validated by `shared-types`' `askFieldSchema`/`answerSchemaFor` on both sides) and `propose_actions` (privileged changes — the AI judges what's privileged — which Congress executes *exactly as approved* over MCP, stopping at the first failure), plus builder mode's `request_builder_mode` and `request_publish` (see "Runtime exhibit types"). Asks land in the calling run's thread (or one new AI thread per run), get an inbox entry, and push to devices only within `maxPushesPerDay` and outside quiet hours (`pushPolicy.ts`). Answers and decisions start a follow-up run in the thread. The Home "Congress asks" strip and one-tap answers read `GET /congress/ai/asks`.

**Memory** (`memory.ts`, `tracking.ts`, `recurrence.ts`, tools in `mcp/memoryTools.ts`, screen at `/chat/memory`): tracked items (`ai_tracking`: the AI's own notes, `nextCheckAt`, an optional code-advanced recurrence, watched events) and facts (`ai_facts`), both in every run's prompt. A self-rescheduling timer runs a background check when an item is due (stamped before the run, retried if refused), when an `immediate` watched event arrives (the AI's own events never count), or on "Check now". Checks reach the owner only through asks.

**Proactive** (`proactive.ts`, `meter.ts`): every published event (via `events.ts`' `onEventPublished`) goes into `ai_event_buffer` and a pure decaying meter (watched events weigh more; a heartbeat grows between looks; quiet hours hold it; a cooldown follows an "act"). Crossing it runs the gate — the cheap `gateModel` (Haiku), tool-less with `--json-schema` — on a digest of recent events, tracked items, open asks and upcoming feed items; only an "act" verdict starts a full proactive run. Both publish `congress.ai_proactive_run`.

No Chamber calls the AI directly; the old `POST /congress/ai/run` was removed along with Chamber processes.

### Google connector

Google sign-in is a core Congress feature (`services/congress/src/connectors/google/`), not any Chamber's: one `google_accounts` table in Congress's DB holds every account's tokens, the OAuth flow lives at `/congress/connectors/google/{start,callback}`, and the owner manages accounts under Settings → Accounts. A Chamber (or connector) declares the scopes it needs (`googleScopes`); connecting always asks for the union of every loaded Chamber's and connector's scopes with incremental consent, so one account serves Calendar and Mail alike. Chambers never see refresh tokens - they call `chamber-kit`'s `listGoogleAccounts()`/`googleAccessToken(accountId, scopes)` through the host, which refreshes (one in-flight refresh per account) and throws `GoogleScopeMissingError`/`GoogleAccountNeedsReconnectError`. Frontends link to `congress-ui`'s `googleConnectHref({ returnTo, loginHint })`. Credentials come from Congress's `.env` (`GOOGLE_OAUTH_*`), falling back to the retired Calendar Chamber's (still on the server) `.env` where they lived before.

**Gmail** (the `gmail` connector, see "Runtime exhibit types") reads mail on top of it and never sends or deletes. It asks for `gmail.modify` only to mark a thread read when the owner opens it (older `gmail.readonly` grants still read).

The Google OAuth callback is the one route exempt from the session cookie: it arrives cross-site, where the `SameSite=Strict` cookie isn't sent, and its single-use `state` (minted only by the session-gated `/start`) authorises it instead.

### WhatsApp: the reader daemon

`services/chamber-whatsapp` holds only the daemon now (no Node package): `reader/` is a separate Go daemon (`wa-reader`, whatsmeow) running as its own system user and systemd unit (`congress-wa-reader`): a read-only WhatsApp linked device that stores messages in its own SQLite files under `data/` and serves a GET-only API on a Unix socket (`WA_READER_SOCKET` in its `.env`), plus `POST /pairing`, which starts the QR linking flow Settings → Connectors shows, and `POST /chats/{jid}/read`, which marks a chat read in its own DB only (unread state comes from the owner's own read receipts, app-state events and history sync; nothing is ever sent back). Congress's `whatsapp` connector (see "Runtime exhibit types") is its only client. **Nothing may ever send or upload anything to WhatsApp**, a permanent owner rule that covers messages, reactions, media, photos, status, read receipts, presence and account/app-state changes, in the UI and for the AI alike. Only `reader/internal/waclient` may import whatsmeow's client, and `reader/readonly-denylist.txt` (enforced by `reader/readonly_test.go` and `tests/wa-reader-readonly.test.ts`) lists every sending/mutating method. Operations, pairing and backups: `services/chamber-whatsapp/reader/README.md`.

### Settings & theming

Owner-wide (not per-device) preferences use a single-row settings table — `id` always `1`, select-then-insert-or-update — via `kit/settings.ts`'s `createSingleRowSettings`. Congress's dark mode setting is applied everywhere (every feed card is a real component in the same document, not an iframe) through `useAppliedTheme`/`useCapitolSettings` in `congress-ui`, plus a pre-paint inline bootstrap script in `frontend/index.html` that applies a cached `localStorage` theme value before first render to avoid a flash of the wrong theme. The home screen's pinned views live on the same Congress settings row (`pinnedViews`, edited in Settings → Home).

### Frontend: mobile-first, always

This is a PWA used on an iPhone first (see `docs/congress-project-brief.md`) — every UI change is designed for a mobile-sized viewport first, with a `@media (min-width: 641px)` override adding desktop chrome on top, never the other way around. Concretely:

- Any new floating/positioned element (a dropdown, popover, panel) defaults to `position: fixed` anchored to the viewport, not `position: absolute` anchored to whatever small trigger button opened it — a trigger near a screen edge is a bad anchor for a panel that can be taller or wider than the space next to it on a phone. `.exhibit-picker-dropdown`/`.exhibit-ref-add-popover`/`.notification-panel` in `packages/congress-ui/src/styles.css` are the reference idiom: fixed to the viewport with `left`/`right: 0.5rem` and `bottom: calc(var(--mobile-nav-height, 0px) + 0.5rem)` by default, switched to a conventional anchored dropdown only inside the desktop media query.
- Before calling any UI change done, actually load it in a browser at a mobile viewport width (~375px) — not just skim the CSS — and check the specific thing you touched still fits and works. A change that only gets checked at desktop width has not been verified.

## Deployment

Full details in `infra/README.md`. Key points to know before pushing to `main`:

- Deploy is push-based, driven by GitHub Actions (`.github/workflows/deploy.yml`), not a server-side poll — **there is no separate deploy step**, pushing to `main` is the deploy. CI builds and tests, then pushes the finished tree to the VPS (`178.105.180.7`) over rsync+SSH and tells it to install runtime deps and restart. The server itself never runs git or a build tool — see `infra/README.md`'s "Deploy: GitHub Actions → server" section for the full flow.
- Congress is the only process (`congress-core`), on port `8000` in production (not `3000`, since that VPS runs other unrelated projects too). The wa-reader daemon is the one other unit (`congress-wa-reader`); its config lives in `services/chamber-whatsapp/.env` on the server.
