# Events and Notifications

`services/congress/src/events.ts` is a small in-process bus, not a log — anything (the type engine, a connector via `ctx.publish`, the AI) calls `publishEvent`, and it hands the event to the AI's observers (`onEventPublished`) and to Congress's own log rules (`eventReceive.ts`), never storing it itself. A throwing handler is logged and never reaches the publisher. Event types are declared in a catalog (a type's `eventPrefix`, a connector's `events`, and `CONGRESS_SYNTHETIC_EVENTS`) which `eventCatalogSync.ts` turns into settings rows (and prunes rows no longer declared). Connectors also get every event through their own `onEvent` (Gmail and Google Calendar forget a disconnected account's data on `google.account_disconnected`).

Log rules (below) are the one consumer of the relayed events that decides what the owner sees:

**Logs** (core Congress: `services/congress/src/eventReceive.ts`, `eventSettings.ts`, `eventHistory.ts`, `notifications.ts`, `pushSubscriptions.ts`; UI under Settings → Logs plus the Notifications tab) is the sole owner of "what should the owner see" — the in-app inbox, Web Push subscriptions and delivery, and a durable history of events worth keeping. It matches incoming events against **event settings** — one auto-derived, never user-created/deleted row per known event type (`event_settings` table, kept current by `eventCatalogSync.ts`): `label`/`description`/`chamber` are a read-only cache of that event's own manifest catalog entry, while `notify` (with its own push title/body/link, `{{payload.x}}`-interpolated) and the history retention are the owner's own editable configuration — except for an exhibit type's events, whose notification choice lives in the type's definition (`eventNotifications`, set by the builder; see [type-engine.md](type-engine.md)) and shows read-only here. Every event is always recorded to history; there is no toggle. A newly-discovered event type defaults to `notify: false` — log everything, notify on nothing until the owner explicitly opts a given event type into pushing. Rows for event types nothing declares any more are deleted on the next catalog sync, so the list only shows what can actually fire. `notify` still dedupes on a template key exactly like the old automations did (an inbox shows current state, so a still-true condition re-firing updates the existing notification rather than piling up duplicates); recording deliberately does not — the `event_history` table is genuinely append-only, since a history is supposed to show what actually happened over time, including repeats. Each history row's own retention is set per-event-type (`historyRetentionMs`, falling back to a 90-day default), independent of Congress's own much-shorter switch. Notifications go stale on their own (`notifications.expiresAt`, swept every minute and filtered on list): an event-driven one expires at its payload's `staleAt` (epoch ms — a time-trigger "before" step such as `starting_soon` stamps its moment, so it vanishes when the event starts), or after 24h by default; `staleAt: null` means "until something else clears it". A time-trigger ladder also dismisses the previous step's notification when the record moves to another step or leaves the ladder (completed, rescheduled, deleted). AI asks have no expiry — they wait for an answer. Already-pushed Web Push can't be retracted; only the inbox entry goes. Because it lives inside Congress, `publishEvent` (`events.ts`) hands every event to `handleReceivedEvent` in-process — no subscription, no HTTP hop, no `getSubscriptions` — before relaying to any subscribing Chambers; `eventCatalogSync.ts` derives event settings from Congress's own registry directly. The inbox is the tab bar's Notifications page (its unread badge on the tab); per-event history lives on each event's Settings → Logs detail view.

"Check a condition, then notify" logic (a Task's due date, an Event about to start) publishes domain events (`task.due_soon`, `task.overdue`, `task.due_cleared`, `event.starting_soon`) rather than pushing a notification directly — the *decision* of whether/what to do about a fired event lives in an editable log rule (or a tracked item Congress's AI watches), not in committed TypeScript. Task's and Event's come from the type engine's time-trigger ladders (see [type-engine.md](type-engine.md)), which fire at the exact instant a threshold is crossed via one self-rescheduling next-wake timer (a single `setTimeout` armed for the soonest upcoming step across every type, re-armed on every record write) rather than a fixed poll interval (a new ladder records past steps silently, and a "before" step reached after its moment isn't announced); the Google Calendar connector polls Google to *discover* events. There is no other way for a notification to reach the inbox, or for an event to trigger a cross-Chamber action: a Chamber that wants something to happen publishes an event and has no idea whether — or how — anything responds to it.
