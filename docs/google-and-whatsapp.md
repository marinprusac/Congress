# Google connector and the WhatsApp reader daemon

### Google connector

Google sign-in is a core Congress feature (`services/congress/src/connectors/google/`), not any Chamber's: one `google_accounts` table in Congress's DB holds every account's tokens, the OAuth flow lives at `/congress/connectors/google/{start,callback}`, and the owner manages accounts under Settings → Accounts. A Chamber (or connector) declares the scopes it needs (`googleScopes`); connecting always asks for the union of every loaded Chamber's and connector's scopes with incremental consent, so one account serves Calendar and Mail alike. Chambers never see refresh tokens - they call `chamber-kit`'s `listGoogleAccounts()`/`googleAccessToken(accountId, scopes)` through the host, which refreshes (one in-flight refresh per account) and throws `GoogleScopeMissingError`/`GoogleAccountNeedsReconnectError`. Frontends link to `congress-ui`'s `googleConnectHref({ returnTo, loginHint })`. Credentials come from Congress's `.env` (`GOOGLE_OAUTH_*`), falling back to the retired Calendar Chamber's (still on the server) `.env` where they lived before.

**Gmail** (the `gmail` connector, see [connectors.md](connectors.md)) reads mail on top of it and never sends or deletes. It asks for `gmail.modify` only to mark a thread read when the owner opens it (older `gmail.readonly` grants still read).

The Google OAuth callback is the one route exempt from the session cookie: it arrives cross-site, where the `SameSite=Strict` cookie isn't sent, and its single-use `state` (minted only by the session-gated `/start`) authorises it instead.

### WhatsApp: the reader daemon

`services/chamber-whatsapp` holds only the daemon now (no Node package): `reader/` is a separate Go daemon (`wa-reader`, whatsmeow) running as its own system user and systemd unit (`congress-wa-reader`): a read-only WhatsApp linked device that stores messages in its own SQLite files under `data/` and serves a GET-only API on a Unix socket (`WA_READER_SOCKET` in its `.env`), plus `POST /pairing`, which starts the QR linking flow Settings → Connectors shows, and `POST /chats/{jid}/read`, which marks a chat read in its own DB only (unread state comes from the owner's own read receipts, app-state events and history sync; nothing is ever sent back). Congress's `whatsapp` connector (see [connectors.md](connectors.md)) is its only client. **Nothing may ever send or upload anything to WhatsApp**, a permanent owner rule that covers messages, reactions, media, photos, status, read receipts, presence and account/app-state changes, in the UI and for the AI alike. Only `reader/internal/waclient` may import whatsmeow's client, and `reader/readonly-denylist.txt` (enforced by `reader/readonly_test.go` and `tests/wa-reader-readonly.test.ts`) lists every sending/mutating method. Operations, pairing and backups: `services/chamber-whatsapp/reader/README.md`.
